# 复刻一个 App：睡前准备 → 夜跑 → 晨检

2026-10-26 用 Typora 跑通一次（成品 mdlive）：准备约 1 小时，无人值守约 8 小时。

当时和对照组 TyporaX（别人用 AI 一夜做的复刻）比了 12 个场景，mdlive 通过 12 个、TyporaX 通过 4 个。这组数不能当结论：

- 场景是看过 TyporaX 的弱点之后挑的，正好落在它文档里写明的取舍上（可视化编辑会规范化 Markdown、扩展语法退回源码模式）。
- 有重复计分：「中文输入法」2 项输掉的真正原因是保存时删了文末换行，和原文保真是同一个根因。
- 中文输入法两边都只用 CDP 模拟过，没在真机上验证。
- 没比的三块 mdlive 明显落后：界面观感、发布（README、图标、安装包）、防护（读写范围、文件大小上限）。这三块夜里没有任何检查。

这次能确认的是方向本身：锁定测试要求的，夜里做到了；没有任何检查的，夜里没人做。

2026-10-30 复查：不给现成的对照实现，只按本方法规划（第 2–4 步），Claude 5 次都定出了同样的核心选择（原文保真为 P0、编辑核心选 CodeMirror 6、不选富文本）；规划漏掉的核心特质由第 2.5 步自造的对照版找出。现成的对照实现不是必需的。

**核心原则**：夜里没人看，Agent 只会朝"能被检查到"的方向努力，检查不到的就当作已完成。所以睡前要把三件事变成机器能判断的东西：
做什么（需求表）、做到什么算完（锁定测试 + 一条验收命令）、哪些不能碰（AGENTS.md 边界）。
观感、交付物、防护也一样：写进需求表，由验收命令或晨检查，夜里才有人做。

模板在 `references/`，每步标了用哪个。工作目录统一用 `~/labs/<代号>/`（`inputs/` 原 App，`evidence/` 拆解证据，`notes/` 方法记录，`run/` 夜跑驱动与日志，`control/` 自造对照版，`checks/` L1 实验脚本，`<代号>/` 新仓库）。

## 0. 选题（人定，5 分钟）

三条都满足才做：

1. 价值主要在客户端，能观察到。云端模型、服务端算法（如 Typeless 的识别与润色）复刻不了，只能换成自己的后端。
2. 能用成熟开源组件拼出来。Agent 擅长组装，不擅长从零写编辑器内核、渲染引擎。
3. 核心行为能自动化测试：有可读回的结果（文件字节、DOM 文本、导出产物）。

产出：一句话目标、"不做什么"清单。有现成的同类实现可以记下当对照组；没有不影响后面各步。

## 1. 环境与配额（Agent，10–20 分钟）

逐项确认，任何一项不满足先解决再往下：

- [ ] **执行模型的配额**：查清速率限制和周期上限（如 GLM 的"5 小时用量上限"）。试跑时第一执行模型大部分时间被限流浪费。
- [ ] **至少两条执行通道**：主力 + 备用，各用一句话冒烟测试确认真能调通（`kll resolve claude-code <模型> --json --launch-env-file <0600 文件>`）。本机 Claude 官方订阅在 CLI 里可能未登录，不要想当然。
- [ ] **凭据不回显**：只检查 env 文件的键名，不打印值。
- [ ] **磁盘**：可用 ≥ 10 GB。Playwright 用系统 Chrome，不下载浏览器。
- [ ] **工具版本**：REA 要求 Node ≥ 24.22.1 或 ≥ 26.12.1，用 fnm 装到独立版本，不改默认 Node；`npm install rea-agents@<版本>` 装在 `~/labs/<代号>/tools`。
- [ ] **GUI 自动化**（需要操作原 App 时）：kimi-cu 在 WebView 类 App 里，后台输入可能进不去，⌘S 会报"无 key window"。可行做法：先点标题栏让窗口成为 key window，再用 AX 菜单命令；输入字符时加 activate。有远程桌面连着时，前台操作会被看到，先告知用户。

## 2. 拆解（Agent + 人确认，30–60 分钟）

**先读许可协议**（安装包或官网的 EULA），按层决定用到哪一层，记进方法记录；L3 以上需要用户明确同意，产出只在本机：

| 层 | 来源 | 价值（Typora 实测） |
| --- | --- | --- |
| L0 | 官方文档、帮助、包内自带文档 | 最高：每个语法、每个行为都有描述，能直接翻成用例 |
| L1 | 试用版实际操作，记录"输入 → 结果"（含保存后的文件字节） | 最高：唯一能拿到测试期望值的来源 |
| L2 | 安装包清单、Info.plist、菜单文字（`rea inspect-artifact` / `inspect-plist`） | 中：结构与平台事实 |
| L3 | 界面文件解码（`rea decode-interface-builder`）、打包代码结构（`rea analyze-javascript-application`） | 菜单解码高（多挖出约 50 项功能）；压缩单文件的代码结构几乎为零 |
| L4 | 反编译、动态调试 | 不做 |

REA 的坑：`decode-interface-builder` 默认最多解 64 个文档，常被 Sparkle 等框架的多语言 nib 占满。解法：把 `Info.plist` 和 `Base.lproj` 下需要的 nib 复制到一个骨架 `.app` 再解。

产出：`references/requirements.md` 格式的需求表。P0 = 核心特质（3–6 条，原 App 的灵魂：从 L0/L1 来，期望值只取 L1 实测；再加上第 2.5 步自造对照组暴露的缺口）；P1 = 功能，模板默认带「健壮性与防护」「交付物」两节；P2 = 不做；附 L1 观察表（每条带证据文件）。**人确认 P0 和 P2**（第 2.5 步做完一起确认），默认的防护和交付物项，人可以划进 P2。

**规划用什么模型**：第 2–4 步是独立的规划步骤，用 Claude 做（默认 Opus）；执行模型不参与定 P0 和架构，夜里只照需求表和 `docs/architecture.md` 做。依据是 2026-10-30 的盲测重放（同一份材料：官方文档 + 拆包事实 + 本方法）：

- 按方法规划，Opus 3/3、Sonnet 1/1、Haiku 1/1 都把「文件即真相」（不改直接保存字节不变，只改一处 diff 也只有一处）定为 P0，L1 计划里都有比对保存字节的实验，编辑核心都选 CodeMirror 6，理由是 ProseMirror 系保存要重新序列化、会改写原文。Grok 1/1 选了 ProseMirror + 自写序列化，没把原文保真当核心。
- 同一个 Sonnet 不按方法、直接「做一个 Typora 风格编辑器」，选了 Milkdown（ProseMirror），自己承认 `source()` 会规范化原文。起作用的是「先定 P0、核心特质决定核心组件」这一步本身，不能让执行 Agent 边做边定架构。
- 「任何 Markdown 都在实时预览中渲染、不退回源码」只有 Sonnet 那 1 次列进了 P0（Opus 0/3、Haiku 0/1）。多跑几次规划补不稳，这类遗漏交给第 2.5 步。

## 2.5 自造对照组（Agent + 人确认）

不加约束地快速做一版，拿第 2 步的 L1 实验去跑它，找规划漏掉的核心特质。2026-10-30 实测：5 次规划漏了 4 次的 R4，这一步找了出来。对照版和脚本都留在 labs，不进新仓库。

1. **造对照版**（另起一个 Agent，可以和第 2 条同时做）：让执行模型在 `~/labs/<代号>/control/` 里做一版，只给一句目标（「做一个 X 风格的 App」）和测试契约（如 `window.app.load/source`、编辑区根元素的 testid），不给需求表、P0、架构，也不给第 2 条的脚本。实测 Sonnet 约 3 分钟做出（Vite + Milkdown）。
2. **写实验脚本，在看对照版之前写好**：把第 2 步的 L1 实验计划写成能对任意构建运行的 Playwright 脚本，放 `~/labs/<代号>/checks/`：`run.mjs <url> <out.json>` 跑全部实验，`compare.mjs` 把结果和原 App 的期望值逐条比。期望值只取 L1 实测，没测过的标 unknown、不比较。实测 79 条实验里 67 条能自动跑（原生对话框、菜单、真输入法等 12 条跳过）；写脚本约 30 分钟，跑一遍约 2 分钟。
3. **跑对照版，按根因分组**：实测有 Typora 答案的 18 项检查里，对照版不同 10 项，归成 3 条根因：保存时规范化原文（4 项）→ R1；光标进入加粗也不露标记（1 项）→ R2；front matter、内嵌 HTML、公式块、任务列表没渲染，下标被错误渲染（5 项）→ R4。
4. **每条根因定去处**：
   - 结构性（由核心组件的选择导致，如富文本序列化改写原文）→ 进 P0，并写进第 3 步当「不选 X」的证据。
   - 覆盖性（只是还没做）→ 是原 App 的标志性行为（L0 反复强调、L1 实测成立）就进 P0，否则进 P1。
5. **人确认**：根因表连同第 2 步的需求表一起给人，确认 P0 和 P2。
6. **局限写进方法记录**：对照版只做了几分钟，覆盖性缺口会偏多；没有原 App 实测答案的实验不能比；推断出来的期望值要标明（这次「不编辑直接保存字节不变」是从「打字再删后保存字节不变」推出的）。

## 3. 定方案（Agent，10 分钟）

架构说明一页：平台、外壳、核心组件，以及"不选什么、为什么"。不选的理由要落到 P0 上，比如"富文本模型要来回转换，必然改写原文"。
原则：核心特质决定核心组件。

## 4. 先写验收（Agent，30–60 分钟，最关键）

1. **锁定测试**（`references/locked-test-guide.md`）：每条 P0 写成测试，期望值取自 L1 实测。测试通过一个小契约读写应用状态（如 `window.<app>.load/source/setCaret`），把契约写进 AGENTS.md。语料文件覆盖边界：BOM、CRLF、无末尾换行、中文、不规整格式。
2. **一条验收命令**（`references/verify.sh`）：哈希校验 → 构建 → 全部测试 → 原生自测 → 文档检查 → 交付物检查（README 与截图、图标、安装包与校验和），任何一步失败即停，最后输出 `VERIFY PASSED`。第 4、6 段按项目改好。
3. **观感量表**（`references/ui-review.md`）：定 3–5 个固定界面状态（怎么到达、截图文件名），连同量表存成 `tests/locked/ui-review.md`，跟锁定测试一起锁。夜里打磨阶段按它自评，晨检按它打分。
4. **对着空壳跑一遍，必须全红但能跑**：试跑时这一步当场抓到 tsconfig 缺 node 类型，不然夜里第一分钟就会卡住。
5. 锁定：`find tests/locked tests/corpus -type f | sort | xargs shasum -a 256 > tests/locked.sha256`，记下这个文件本身的哈希，提交基线。

## 5. 写任务书（Agent，10 分钟）

- `AGENTS.md`（`references/AGENTS.template.md`）：边界、锁定测试规则与契约、验收、遇阻处理、顺序。
- `docs/progress.md`：勾选清单，含需求表的「健壮性与防护」「交付物」两节。最后一项完成后在第一行写 `ALL_DONE`，下面留"打磨"一节。
- `run/KICKOFF.md`（`references/KICKOFF.md`）：每轮的启动指令。

**发给用户过目**：准备好的东西、怎么跑、要确认的三件事（跳过权限确认、用量、屏幕会弹窗）。用户同意后启动。

## 6. 夜跑（无人值守）

`references/overnight.sh` + `references/launch.py`，在 tmux 里跑：

```bash
cp references/{overnight.sh,launch.py} ~/labs/<代号>/run/
echo '{"glm":"glm-5.3","opus":"claude-opus-5-5"}' > ~/labs/<代号>/run/models.json   # 简称 → CLI 模型名，与 *.env 同名
tmux new-session -d -s <代号>-overnight "env -u CLAUDECODE -u CLAUDE_CODE_SESSION_ID -u CLAUDE_CODE_CHILD_SESSION \
  REPO=~/labs/<代号>/<代号> RUN_DIR=~/labs/<代号>/run DEADLINE=<epoch 秒> CLAUDE_BIN=<claude 绝对路径> zsh ~/labs/<代号>/run/overnight.sh"
```

tmux 里 PATH 可能找不到 claude（fnm 安装的尤其如此），所以用 `CLAUDE_BIN` 给绝对路径。驱动已用假 Agent 冒烟测试过：清单阶段→打磨阶段切换、按时长结束本轮、配额退避都正常。

- 每轮一个新会话，所有状态放在仓库里（git + progress.md）。中途断了，下一轮从工作区继续；GLM 被限流时写到一半的代码，就是这样被 Opus 接上的。
- 自动换模型：连续两轮没有新提交就换备用模型；`run/FORCE_MODEL` 可以人工锁定模型。
- **按错误类型退避**：限流（429，含"N 小时上限"）等到重置时间或指数退避，不要立刻重试；网关故障（503）短退避后换通道。
- 换会话的条件按时长判断（如单轮 ≥ 90 分钟）或连续无提交判断，不靠"上下文满了"：Opus 靠自动压缩，单轮能跑 4 小时，从来不会触发。
- `ALL_DONE` 后自动进入打磨阶段（`KICKOFF-polish.md`），跑到截止时间。
- 结束时跑一次总验收，日志写进 `run/logs/`。

botmux 定时任务两个，都用 `--topic` 建在当前话题：

- 每 2 小时一次**静默巡检**（`--silent`）：会话在不在、2 小时内有没有提交、磁盘、锁定哈希、是否连续限流。只在异常时报警，夜跑结束后自删。
- **晨检**（一次性，结束后半小时）：prompt 用 `references/morning-review.md`。provider 故障会让它延后，prompt 里要写"失败后 30 分钟重试"。

## 7. 晨检（Agent，30–60 分钟）

照 `references/morning-review.md` 做，结论发到话题：

1. 锁定测试指纹与 git 历史（只应有基线提交）。
2. 越界审计（`references/audit.py`）：所有命令与写文件路径，查有没有写到项目外、推送、全局安装、读 inputs/evidence、改系统配置。
3. 独立重跑总验收；没提交的遗留改动先 `git stash`，不要混进验收。
4. 交付物与防护：验收命令只查了文件在不在。再核对 README 写的每项能力都已实现、截图是当前界面、安装包装上能用；需求表「健壮性与防护」每条都有测试且通过。
5. 观感评审（`references/ui-review.md`）：用当前构建重截固定界面状态，人或视觉模型按量表打分，结论写明谁评的。夜里 Agent 的自评只作参考。
6. 对照组比较（有对照组才做，`references/compare-template.mjs`）：场景由没看过任何一方实现的 Agent 从原 App 官方功能清单里盲选，选定后不增删；同样的点击和按键，按用户能拿到的结果判定；按根因去重计分；模拟输入的场景（如 CDP 输入法事件）标「模拟」；结论写清哪些维度没比。
7. 亲手打开真 App 抽查 2–3 项核心特质。
8. 结论按固定结构写：一句话结论 → 测试 → 越界审计 → 交付物与防护 → 观感 → 对照 → 各模型贡献 → 方法上学到的 → 需要人亲手确认的。

**收尾**：把这次的新教训改进本技能（短分支 + PR）；方法记录 `notes/method-log.md` 留在 labs，不进仓库。

## 方法记录

全程在 `notes/method-log.md` 按时间记一行一事：每一步的耗时、踩过的坑、用户的决定。晨检和改进本技能都靠它。时间写本机时区，并注明和北京时间的换算。
