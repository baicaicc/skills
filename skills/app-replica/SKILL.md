# 复刻一个 App：睡前准备 → 夜跑 → 晨检

2026-10-26 用 Typora 跑通过一次（无人值守约 8 小时），确认了：锁定测试要求的，夜里做到了；没有任何检查的（观感、发布、防护），夜里没人做。
10-30 又复查了规划和自造探针版的做法。数字、局限与出处见 `references/evidence-2026-10.md`。

**核心原则**：夜里没人看，Agent 只会朝"能被检查到"的方向努力，检查不到的就当作已完成。所以睡前要把三件事变成机器能判断的东西：
做什么（需求表）、做到什么算完（锁定测试 + 一条验收命令）、哪些不能碰（AGENTS.md 边界）。
交付物和防护也写进需求表，观感锁原版在几个界面状态下的截图，由验收命令或晨检查，夜里才有人做。
人只在睡前回一张卡（第 5 步，回「行」就启动），早上看结果；「常设授权」里的事不再问，技术选择也不问人。

模板在 `references/`，每步标了用哪个。工作目录统一用 `~/labs/<代号>/`（`inputs/` 原 App，`evidence/` 拆解证据，`notes/` 方法记录，`run/` 夜跑驱动与日志，`control/` 第 2.5 步探针版的存档（不是晨检的对照组），`checks/` L1 实验脚本与答案，`<代号>/` 新仓库）。

## 常设授权（确认一次，之后每次复刻都照这里做）

1. **无人值守跳过权限确认**：夜跑 Agent 以跳过权限确认模式运行；边界照 AGENTS.md（只写 `~/labs/<代号>/`、不推送不发布、不全局安装、不改系统配置、不读 inputs/evidence/control/checks），晨检越界审计兜底。
2. **用量**：一次夜跑最多约 10 小时；执行通道按需求选主力 + 备用；配额用尽时按错误类型等待或换通道，两条都用尽就停，早上报告，不半夜叫人。
3. **屏幕**：允许在执行机上弹窗、用 GUI 自动化操作原 App 试用版；检测到有人远程桌面连着时，先在话题里说一声再操作（通知，不等回复）。
4. **拆解层级**：L0–L3 默认做，产出只留本机、不公开；L4 不做。许可协议禁止逆向时仍按「只在本机、不公开」做，并记进方法记录。
5. **工具与试用版**：允许下载原 App 试用版、在 `~/labs/<代号>/tools` 装 REA、用 fnm 装独立 Node 版本。

登录、扫码、付费：

- **已有登录态就直接用，不问**：本机已登录的 CLI、浏览器会话、已存的凭据文件、能用现有凭据换出的令牌，都算有登录态。凭据不回显、不复制到别的机器。
- **一切以目标为主**：不为少打扰用户而降级目标，不为绕开扫码或付费换成试用版、免费额度凑合，也不跳过功能。
- 达成目标需要用户本人扫码或付费时：立刻在话题里找用户确认，写清要做什么、为什么需要、代价多少。等回复期间先做不依赖它的项，不停工、不降级。夜里也照发，用户醒来处理。
- 付费只由用户本人完成，Agent 不自己付。

仍要停下来问的：

- 要删用户的文件或别的项目来腾磁盘。
- 超出上面任何一条的边界。

## 0. 选题（人定，5 分钟）

三条都满足才做：

1. 价值主要在客户端，能观察到。云端模型、服务端算法（如 Typeless 的识别与润色）复刻不了，只能换成自己的后端。
2. 能用成熟开源组件拼出来。Agent 擅长组装，不擅长从零写编辑器内核、渲染引擎。
3. 核心行为能自动化测试：有可读回的结果（文件字节、DOM 文本、导出产物）。

产出：一句话目标、"不做什么"清单。有现成的同类实现可以记下，当晨检的对照组；没有不影响后面各步。

## 1. 环境与配额（Agent 自查，10–20 分钟）

逐项自查，任何一项不满足先解决再往下。已有登录态直接用；要用户本人扫码或付费的，照「常设授权」立刻在话题里找用户确认，先做别的。

- [ ] **执行模型的配额**：查清速率限制和周期上限（如 GLM 的"5 小时用量上限"）。试跑时第一执行模型大部分时间被限流浪费。
- [ ] **至少两条执行通道**：主力 + 备用，各用一句话冒烟测试确认真能调通（`kll resolve claude-code <模型> --json --launch-env-file <0600 文件>`）。本机 Claude 官方订阅在 CLI 里可能未登录，不要想当然。
- [ ] **凭据不回显**：只检查 env 文件的键名，不打印值。
- [ ] **磁盘**：可用 ≥ 10 GB。Playwright 用系统 Chrome，不下载浏览器。
- [ ] **工具版本**：REA 要求 Node ≥ 24.22.1 或 ≥ 26.12.1，用 fnm 装到独立版本，不改默认 Node；`npm install rea-agents@<版本>` 装在 `~/labs/<代号>/tools`。
- [ ] **GUI 自动化**（需要操作原 App 时）：kimi-cu 在 WebView 类 App 里，后台输入可能进不去，⌘S 会报"无 key window"。可行做法：先点标题栏让窗口成为 key window，再用 AX 菜单命令；输入字符时加 activate。有人远程桌面连着时，先在话题里说一声再操作（常设授权第 3 条，不等回复）。

## 2. 拆解（Agent，30–60 分钟）

**规划用 Claude**：第 2–4 步是独立的规划步骤，用 Claude 做（这次 Opus、Sonnet、Haiku 的核心选择一致；默认用 Opus 是偏好，不是数据结论）。架构要在规划阶段对着 P0 定下来；执行模型不参与定 P0 和架构，夜里只照需求表和 `docs/architecture.md` 做。依据：只给一句目标时，执行模型边做边选出了会改写原文的架构（证据文件「规划复查」）。

**先读许可协议**（安装包或官网的 EULA），结论记进方法记录；L0–L3 默认做，L4 不做，产出只留本机（常设授权第 4 条）：

| 层 | 来源 | 价值（Typora 实测） |
| --- | --- | --- |
| L0 | 官方文档、帮助、包内自带文档 | 最高：每个语法、每个行为都有描述，能直接翻成用例 |
| L1 | 试用版实际操作，记录"输入 → 结果"（含保存后的文件字节） | 最高：唯一能拿到测试期望值的来源 |
| L2 | 安装包清单、Info.plist、菜单文字（`rea inspect-artifact` / `inspect-plist`） | 中：结构与平台事实 |
| L3 | 界面文件解码（`rea decode-interface-builder`）、打包代码结构（`rea analyze-javascript-application`） | 菜单解码高（多挖出约 50 项功能）；压缩单文件的代码结构几乎为零 |
| L4 | 反编译、动态调试 | 不做 |

REA 的坑：`decode-interface-builder` 默认最多解 64 个文档，常被 Sparkle 等框架的多语言 nib 占满。解法：把 `Info.plist` 和 `Base.lproj` 下需要的 nib 复制到一个骨架 `.app` 再解。

产出：

- 需求表草稿（`references/requirements.md` 格式）。P0 = 核心特质（3–6 条，原 App 的灵魂：从 L0/L1 来，期望值只取 L1 实测；再加上第 2.5 步自造探针版暴露的缺口）；P1 = 功能，模板默认带「健壮性与防护」「交付物」两节，不适用的由 Agent 划进 P2 并写一句理由；P2 = 不做。
- L1 实验计划：每条写清操作、读回什么（保存后的字节、可见文本）、对应哪条需求。实际操作放到第 2.5 步，跑完探针版再定先测哪些。

## 2.5 自造探针版（Agent，约 80–100 分钟，含 L1 与原版截图约 40 分钟；未实测全流程）

快速、不加约束地做一版，拿 L1 实验去跑它。用处有两个：用它的实际失败坐实第 3 步的「不选 X」；补规划漏掉的需求条目。它只用于规划，不是晨检的对照组。依据与局限见证据文件「自造探针版」。

1. **造探针版**（另起一个 Agent，和第 2 条同时做）：放在 labs 之外的独立目录 `/tmp/<代号>-probe/`。提示词只给一句目标（「做一个 X 风格的 App」）、测试契约（如 `window.app.load/source`、编辑区根元素的 testid）和读写范围（「只在 /tmp/<代号>-probe/ 里读写；不读这台机器上的其他目录」）；不给需求表、P0、架构。做完拷进 `~/labs/<代号>/control/` 存档，不带 node_modules、dist 等生成物，再删掉 /tmp 里那份（夜跑的越界审计不查 /tmp）：
   `mkdir -p ~/labs/<代号>/control && tar -C /tmp/<代号>-probe --exclude node_modules --exclude dist --exclude build -cf - . | tar -C ~/labs/<代号>/control -xf - && rm -rf /tmp/<代号>-probe`
2. **写实验脚本，在看探针版之前写好**：把 L1 实验计划写成能对任意网页构建运行的 Playwright 脚本，放 `~/labs/<代号>/checks/`。`run.mjs <url> <out.json>` 跑全部实验，记下读回的结果；`compare.mjs <answers.json> <out.json>` 把结果和原 App 的答案逐条比。`answers.json` 只放 L1 实测，没测过的写 unknown、不比较，推断出来的标明。
3. **先跑探针版**，拿到它在每条实验上的原始结果。
4. **再做 L1**（约 30 分钟）：先保证每条 P0 草稿都有实测期望值；剩下的时间优先测「探针版结果可疑、L0 又有明确描述」的实验。结果写进需求表的 L1 观察表和 `answers.json`。原 App 是网页时，直接用同一个脚本跑原 App 拿答案。同时按 `references/ui-review.md` 用同一份示例文档截原版的几个固定界面状态，存 `~/labs/<代号>/evidence/ui-target/`。
5. **比较，按根因分组**：同一根因的多项差异合成一条。
6. **每条根因定去处**（Agent 自己定，不问人）。判据：修它要换核心组件或绕开其数据模型 → 结构性；加插件、渲染器或配置能修 → 覆盖性；拿不准就标「拿不准」。
   - 结构性 → 进 P0，并写进第 3 步当「不选 X」的证据（如富文本保存要重新序列化，会改写原文）。
   - 覆盖性 → 是原 App 的标志性行为（L0 反复强调、L1 实测成立）就进 P0，否则进 P1。
   - 另起一个 Agent，不给它第一份结论，按同样的判据独立再分一次。两份不一致或标「拿不准」的，一律进 P0：多锁一条的代价是夜里多做点，少锁一条的代价是核心特质被做坏（例：证据文件里的 R2）。理由记进方法记录。
7. **局限写进方法记录**：探针版只做了几分钟，覆盖性缺口会偏多；没有原 App 答案的实验不能比，能查出多少取决于 L1 测了哪些；推断出来的答案要标明。

## 3. 定方案（Agent，10 分钟）

架构说明一页：平台、外壳、核心组件，以及"不选什么、为什么"。不选的理由要落到 P0 上，比如"富文本模型要来回转换，必然改写原文"；第 2.5 步的结构性缺口就是现成的证据。
原则：核心特质决定核心组件。

## 4. 先写验收（Agent，30–60 分钟，最关键）

1. **锁定测试**（`references/locked-test-guide.md`）：每条 P0 写成测试，期望值取自 L1 实测。测试通过一个小契约读写应用状态（如 `window.<app>.load/source/setCaret`），把契约写进 AGENTS.md。语料文件覆盖边界：BOM、CRLF、无末尾换行、中文、不规整格式。
2. **一条验收命令**（`references/verify.sh`）：哈希校验 → 构建 → 全部测试 → 原生自测 → 文档检查 → 交付物检查（README 与截图、图标、安装包与校验和），任何一步失败即停并说明原因，最后输出 `VERIFY PASSED`。第 4、6 段按项目改好；划进 P2 的交付物，锁定前删掉第 6 段对应几行。
3. **观感基准**（`references/ui-review.md`）：把第 2.5 步截的原版截图和 `states.md` 拷进 `tests/locked/ui-target/`，示例文档放进 `tests/corpus/`，跟锁定测试一起锁。目标是和原版看起来同一路，但自己写，不用原版的主题、字体、图标、文案。
4. **对着空壳跑一遍，必须全红但能跑**：试跑时这一步当场抓到 tsconfig 缺 node 类型，不然夜里第一分钟就会卡住。第 3 段红了后面不会跑，所以再放上带三节标题的 `docs/validation.md`（留作骨架），以及占位的 README（带一张截图）、图标和 `scripts/package.sh`，跑 `VERIFY_FROM=5 bash scripts/verify.sh`，应输出 `VERIFY PARTIAL`；跑通后删掉 README、图标、package.sh 这几个占位。

## 5. 写任务书、发确认卡、锁定（Agent，15–20 分钟）

- `AGENTS.md`（`references/AGENTS.template.md`）：边界、锁定测试规则与契约、验收、遇阻处理、顺序。
- `docs/progress.md`：勾选清单，含需求表的「健壮性与防护」「交付物」两节。最后一项完成后在第一行写 `ALL_DONE`，下面留"打磨"一节。
- `run/KICKOFF.md`（`references/KICKOFF.md`）：每轮的启动指令。

**睡前确认卡**（`references/confirm-card.md`）：人只在这里确认一次，回「行」就启动。卡上只有两样，用用户的话写：

- 「和原版一样、会保证的 N 件事」：每条 P0 写成一句能亲手验的话（做什么 → 会看到什么）。用户只在有不在乎的、或漏了在乎的时候才说。
- 「这次不做」：P2 用大白话列出。

技术选择不上卡；跳过权限确认、用量、屏幕弹窗照「常设授权」办，也不上卡。

收到回复后照模板「收到回复后」一节改需求表，然后**锁定**：`(find tests/locked tests/corpus -type f; printf '%s\n' scripts/verify.sh playwright.config.ts) | sort | xargs shasum -a 256 > tests/locked.sha256`（还有别的决定跑哪些测试的配置文件，一起加进去），记下这个文件本身的哈希，提交基线，基线提交号写进 `run/baseline-commit`（命令见 `references/locked-test-guide.md`）。锁定后再启动夜跑。

## 6. 夜跑（无人值守）

`references/overnight.sh` + `references/launch.py`，在 tmux 里跑：

```bash
cp references/{overnight.sh,launch.py} ~/labs/<代号>/run/
echo '{"glm":"glm-5.3","opus":"claude-opus-5-5"}' > ~/labs/<代号>/run/models.json   # 简称 → CLI 模型名，与 *.env 同名
tmux new-session -d -s <代号>-overnight "env -u CLAUDECODE -u CLAUDE_CODE_SESSION_ID -u CLAUDE_CODE_CHILD_SESSION \
  REPO=~/labs/<代号>/<代号> RUN_DIR=~/labs/<代号>/run DEADLINE=<epoch 秒> CLAUDE_BIN=<claude 绝对路径> zsh ~/labs/<代号>/run/overnight.sh"
```

`DEADLINE` 不超过启动后 10 小时（常设授权第 2 条，驱动会拒绝更长的）。tmux 里 PATH 可能找不到 claude（fnm 安装的尤其如此），所以用 `CLAUDE_BIN` 给绝对路径。驱动已用假 Agent 冒烟测试过：清单阶段→打磨阶段切换、按时长结束本轮、配额退避都正常。

- 每轮一个新会话，所有状态放在仓库里（git + progress.md）。中途断了，下一轮从工作区继续；GLM 被限流时写到一半的代码，就是这样被 Opus 接上的。
- 自动换模型：连续两轮没有新提交就换备用模型；`run/FORCE_MODEL` 可以人工锁定模型。主力和备用的配额都要到截止时间以后才重置时，驱动提前结束，早上报告。
- **按错误类型退避**：限流（429，含"N 小时上限"）等到重置时间或指数退避，不要立刻重试；网关故障（503）短退避后换通道。
- 换会话的条件按时长判断（如单轮 ≥ 90 分钟）或连续无提交判断，不靠"上下文满了"：Opus 靠自动压缩，单轮能跑 4 小时，从来不会触发。
- `ALL_DONE` 后自动进入打磨阶段（`KICKOFF-polish.md`），跑到截止时间。
- 结束时跑一次总验收，日志写进 `run/logs/`。

botmux 定时任务两个，都用 `--topic` 建在当前话题：

- 每 2 小时一次**静默巡检**（`--silent`）：会话在不在、2 小时内有没有提交、磁盘、锁定哈希、是否连续限流。只在异常时报警，夜跑结束后自删。
- **晨检**（一次性，结束后半小时）：prompt 用 `references/morning-review.md`。provider 故障会让它延后，prompt 里要写"失败后 30 分钟重试"。

## 7. 晨检（Agent，30–60 分钟）

照 `references/morning-review.md` 做，结论发到话题：

1. 锁定文件（测试、语料、`scripts/verify.sh`、`playwright.config.ts`）：哈希一致，和基线提交的 diff 为空，git 历史只有基线提交。
2. 越界审计（`references/audit.py`）：所有命令与读写文件的路径，查有没有写到项目外、推送、全局安装、读 inputs/evidence/control/checks、改系统配置。
3. 独立重跑总验收（直接 `bash scripts/verify.sh`）；没提交的遗留改动先 `git stash`，不要混进验收。
4. 交付物与防护：验收命令只查了文件在不在。再核对 README 写的每项能力都已实现、截图是当前界面、安装包装上能用；需求表「健壮性与防护」每条都有测试且通过。
5. 观感对照（`references/ui-review.md`）：按 `tests/locked/ui-target/states.md` 截当前构建，视觉模型逐张和 `tests/locked/ui-target/` 的原版截图比，给一致程度和缺陷清单（溢出、错位、对比度不够、深色模式坏掉）；报告里原版和当前截图并排放，写明谁评的。夜里 Agent 的自评只作参考。
6. L1 实验重跑：用第 2.5 步的 `checks/` 对当前构建跑一遍，和 L1 答案比；unknown 不算，按根因去重。不需要现成的对照实现。
7. 对照组比较（有现成的同类实现才做；`control/` 的探针版不算；`references/compare-template.mjs`）：场景由没看过任何一方实现的 Agent 从原 App 官方功能清单里盲选，选定后不增删；同样的点击和按键，按用户能拿到的结果判定；按根因去重计分；模拟输入的场景（如 CDP 输入法事件）标「模拟」；结论写清哪些维度没比。
8. 亲手打开真 App 抽查 2–3 项核心特质。
9. 结论按固定结构写：一句话结论 → 测试 → 越界审计 → 交付物与防护 → 观感（原版与当前截图并排）→ L1 重跑 → 对照 → 各模型贡献 → 方法上学到的 → 需要人亲手确认的。

**收尾**：把这次的新教训改进本技能（短分支 + PR）；方法记录 `notes/method-log.md` 留在 labs，不进仓库。
